في الفصل 16 الحسبة كلها بتتغير. المقارنات بقت ببلاش تقريبًا، واللي بيكلّف بجد هو قراية **صفحة** من الديسك (probe). فالسؤال بقى: كام صفحة لازم نقرا عشان نلاقي مفتاح وسط مليار؟ والإجابة في الفصل كله رقم صغير جدًا، 2 أو 3. التمارين هنا ليها تلات أشكال: «احسب log\_M N وشوف قد إيه صغير»، و«ارسم الـ B tree أو الـ extendible hash table بعد الـ inserts دي»، و«حاكي نمو الصفحات وشوف هتبقى مليانة قد إيه».

:::goal هدف الدرس:
تحس بحجم log\_M N، وتبني ISAM وB tree بالإيد وتعرف إمتى وفين بيحصل الـ split، وتفرّق بين الـ B tree اللي في الكتاب (index) وشجرة 3-4-5-6 المجردة، وتبني extendible hash table وتفهم الدليل بيتضاعف ليه، وتقيس الصفحات بتتملي قد إيه في B tree وB\* وextendible hashing.
:::

:::

### تمرين 16.1، 16.21 و16.12: log\_M N صغير قد إيه؟

:::problem
(16.1) اعمل جدول بقيم log\_M N لـ M = 10 و100 و1000، وN = 10³ و10⁴ و10⁵ و10⁶. (16.21) اعمل جدول بالفرق بين log₉₉₉ N وlog₁₀₀₀ N لنفس قيم N. (16.12) افترض إن عندنا شجرة من 3 مستويات، ونقدر نشيل a links في الميموري، وفي صفحات الـ nodes الداخلية من b لـ 2b link، وفي الصفحات الخارجية من c لـ 2c item. إيه أقصى عدد items تقدر الشجرة دي تشيله، كـ function في a وb وc؟
:::

:::think
الصفحة اللي فيها M entry بتقسم مساحة البحث M حتة مرة واحدة. فبعد h صفحة نقدر نفرّق بين M^h مفتاح، يعني h = log\_M N. ولـ 16.21: log₉₉₉ N − log₁₀₀₀ N = ln N × (1/ln 999 − 1/ln 1000)، ده رقم صغير جدًا. ولـ 16.12: أقصى عدد بيحصل لما كل الصفحات تبقى مليانة لآخرها.
:::

:::solution
```
16.1 log_M N:
        N \ M         10        100       1000
         1000       3.00       1.50       1.00
        10000       4.00       2.00       1.33
       100000       5.00       2.50       1.67
      1000000       6.00       3.00       2.00
16.12 three levels: a links in memory -> pages with b..2b links -> pages with c..2c items
     maximum = a * 2b * 2c = 4abc items   (minimum a*b*c)
     e.g. a = 1000, b = c = 500: max 1000000000 items, min 250000000; still 2 probes per search
16.21 log_999 N - log_1000 N:
     N =     1000: 1.000145 - 1.000000 = 0.000145
     N =    10000: 1.333526 - 1.333333 = 0.000193
     N =   100000: 1.666908 - 1.666667 = 0.000241
     N =  1000000: 2.000290 - 2.000000 = 0.000290
```

بص على الجدول: بصفحة فيها 1000 entry، المليون مفتاح محتاجين صفحتين بس، وأي حاجة أقل من مليار محتاجة 3. وده سبب إننا في الكلام العملي بنقول «عدد ثابت من الـ probes». 16.12: الأقصى a × 2b × 2c = 4abc (والأقل a × b × c). يعني لو a = 1000 وb = c = 500 تشيل مليار item، وأي بحث فيه صفحتين بس من الديسك، لأن المستوى الأولاني في الميموري. 16.21: الفرق أقل من 0.0003 حتى عند المليون. يعني لو شلت item واحد من كل node مش هتفرق، وده بالظبط اللي بيسمح لـ Program 16.3 إنه يقسم الـ node وهي فيها M بدل M−1.
:::

### تمرين 16.2 و16.3: ISAM والمكان الفاضي

:::problem
(16.2) ارسم indexed sequential file (ISAM) للمفاتيح 516، 177، 143، 632، 572، 161، 774، 470، 411، 706، 461، 612، 761، 474، 774، 635، 343، 461، 351، 430، 664، 127، 345، 171، 357، لـ M = 5 وM = 6. (16.3) افترض إننا بنبني ISAM لـ N item في صفحات حجمها M، بس سايبين k مكان فاضي في كل صفحة عشان التوسّع. اكتب معادلة لعدد الـ probes في البحث بدلالة N وM وk، واستعملها تحسب عدد الـ probes لما k = M/10، لـ M = 10 و100 و1000 وN = 10³ لحد 10⁶.
:::

:::think
الـ ISAM ببساطة: نرتّب المفاتيح، ونقسمهم على صفحات مليانة كل واحدة فيها M، وبعدين نعمل صفحة index فيها أول مفتاح من كل صفحة، ونكرر لحد ما يفضل صفحة واحدة. والبحث: في كل صفحة index، دوّر على آخر مفتاح ≤ المفتاح اللي بتدوّر عليه، وامشي وراه. ولـ 16.3: لو سايبين k مكان فاضي، كل صفحة (data أو index) بقت بتشيل M − k بس، فعدد المستويات ⌈log\_(M−k) N⌉.
:::

:::solution
```

     M = 5: data pages (sorted, full):
       127 143 161 171 177 | 343 345 351 357 411 | 430 461 461 470 474 | 516 572 612 632 635 | 664 706 761 774 774
       index level 1 (5 entries = first key of each page below):
       127 343 430 516 664
       levels = 2: search 635 -> hit in 2 probes, search 500 -> miss in 2 probes
     M = 6: data pages (sorted, full):
       127 143 161 171 177 343 | 345 351 357 411 430 461 | 461 470 474 516 572 612 | 632 635 664 706 761 774 | 774
       index level 1 (5 entries = first key of each page below):
       127 345 461 632 774
       levels = 2: search 635 -> hit in 2 probes, search 500 -> miss in 2 probes
16.3 probes = ceil(log_(M-k) N); with k = 0 vs k = M/10:
        N \ M       10 (k=0) (k=M/10)      100 (k=0) (k=M/10)     1000 (k=0) (k=M/10)
         1000             3(3.00)    4(3.14)             2(1.50)    2(1.54)             1(1.00)    2(1.02)
        10000             4(4.00)    5(4.19)             2(2.00)    3(2.05)             2(1.33)    2(1.35)

     only where N sat exactly on a power of M (a full tree with no room left), never by more
```

في الحالتين الـ 25 مفتاح عملوا 5 صفحات data وصفحة index واحدة فوقهم، فأي بحث = 2 probe. ولاحظ إن 774 و461 متكررين وقاعدين جنب بعض، ودي ميزة الملف المترتب. وفي M = 6 آخر صفحة فيها مفتاح واحد بس.

16\.3: لما تسيب 10% فاضي، القيمة الحقيقية (اللي بين القوسين) بتزيد من 1% لـ 5% بس. والرقم المقرّب بيزيد واحد في الحالات اللي N فيها كان قوة لـ M بالظبط، يعني شجرة كانت مليانة على الآخر ومفيهاش أي مكان. والمكسب إن الـ inserts الجاية هتلاقي مكان من غير ما تعيد بناء الملف. يعني المكان الفاضي ده رخيص جدًا.
:::

### تمرين 16.5 و16.10: شجرة 3-4-5-6 بالـ top-down

### تمرين 16.11، 16.13 و16.16: محاكاة نمو الصفحات وB\*

:::problem
(16.11) اكتب برنامج يحسب متوسط عدد الصفحات الخارجية لـ B tree من order M اتبنى من N insert عشوائي، باستعمال العملية الاحتمالية اللي بعد Property 16.1، لـ M = 10 و100 و1000 وN = 10³ لحد 10⁶. (16.13) فكّر في الـ sibling split (أو B\* tree): لما node يجي وقت إنها تتقسم، بنضمها مع جارتها. لو الجارة فيها k entry وk \< M − 1، نوزّع الـ items عليهم بحيث كل واحدة تاخد حوالي (M + k)/2. غير كده، نعمل node جديدة ونوزّع على التلاتة كل واحدة حوالي 2M/3. اكتب حدود عدد الـ probes في البحث أو الـ insert في B\* tree، وقارنها بالـ B tree. (16.16) اعمل محاكاة احتمالية تحسب متوسط عدد الصفحات مع الـ sibling split لنفس M وN.
:::

:::think
مش محتاجين نبني الشجرة خالص. اللي يهمنا الصفحات الخارجية وكل واحدة فيها كام. والمفتاح العشوائي بيقع في صفحة باحتمال على قد حجمها (كل فراغ بين مفتاحين ليه نفس الفرصة)، وده الـ Markov chain بتاع Yao. والحيلة: نختار صفحة عشوائي، ونقبلها باحتمال size/M (rejection sampling)، كأننا اخترنا item عشوائي. ولـ B\* محتاجين الجيران بجد، فبنحط الصفحات في linked list بالترتيب. ولـ 16.13: في B tree كل node جوه فيها من M/2 لـ M link، فالارتفاع بين log\_M N وlog\_(M/2) N. وفي B\* كل node فيها على الأقل 2M/3، فالحد الأعلى بيبقى log\_(2M/3) N.
:::

### تمرين 16.27: كام صفحة هتبقى فاضية؟

:::problem
لو استعملنا directory حجمه 32 في Figure 16.10، كام صفحة هتبقى فاضية؟

:::think
Figure 16.10 فيها 24 مفتاح octal (001، 017، 061، 107، … 766)، يعني كل واحد 9 بت. الدليل بتاع 8 خانات بيبص على أول 3 بتات. ولو الدليل 32 يبقى بيبص على أول 5 بتات، ولو كل خانة ليها صفحة لوحدها، الصفحة هتبقى فاضية لما مايكونش فيه ولا مفتاح بيبدأ بالـ 5 بتات دي. يعني نكتب أول 5 بتات من كل مفتاح ونعدّ اللي مش موجود.

:::solution
```
16.27 Figure 16.10: 24 keys (octal, 9 bits). Directory of 8 (3 bits): 0 of the 8 prefixes
      are empty, so 7 pages suffice (slots 010 and 011 share the '01' page).
      Directory of 32 (5 bits), one page per slot: 14 of the 32 pages would be EMPTY:
       00001 00010 00101 01001 01010 01100 01101 01110 10000 10010 10011 10110 11001 11011
      (with page sharing, extendible hashing still uses only the 7 real pages)
```

14 صفحة من 32 هتبقى فاضية، يعني قرب النص. وده بالظبط ليه الـ extendible hashing بيخلّي كذا خانة تشاور على نفس الصفحة: الدليل بيكبر عادي، بس الصفحات مابتتعملش غير لما يبقى فيه مفاتيح تتحط فيها.

### تمرين 16.28، 16.29، 16.38 و16.39: بناء extendible hash table

:::problem
(16.28) ارسم رسومات زي Figures 16.11 لحد 16.13 توضّح إدخال المفاتيح 562، 221، 240، 771، 274، 233، 401، 273، 201 بالترتيب ده في جدول فاضي، بـ M = 5. (16.29) نفس المفاتيح بالترتيب المعكوس: هل الجدول هيتغير؟ (16.38) اعمل الـ sort لـ extendible hash table. (16.39) اعمل الـ select.

(البرنامج هنا بيسيب الصفحة تشيل M بالظبط، وبيقسم لما تعدّيها، زي Exercise 16.37). والـ sort بسيط: الدليل نفسه مترتب بالبتات، فبنلف عليه ونتخطى الـ pointers المكررة.

:::solution
::figure ex16-ext

### تمرين 16.30، 16.31 و16.32: البناء من ملف مترتب، ودليل بـ 8 pointers لصفحة واحدة

:::problem
(16.30) لو معاك array من items مترتبة، هتعرف حجم الدليل بتاع الـ extendible hash table بتاعها إزاي؟ (16.31) اكتب برنامج يبني extendible hash table من array مترتبة في لفّتين: لفة تحدد حجم الدليل، ولفة توزّع الـ items على الصفحات وتملى الدليل. (16.32) اديني مجموعة مفاتيح الـ extendible hash table بتاعها دليله حجمه 16، وفيه 8 pointers بتشاور على صفحة واحدة.
:::

:::think
16\.30: في الترتيب المترتب، المفاتيح اللي ليها نفس أول d بت بتبقى ورا بعض. فـ d هو أصغر عدد بتات يخلّي كل مجموعة من دول فيها M أو أقل. (مجموعة فيها M + 1 مفتاح متفقين في أول j بت معناها إن d لازم يبقى أكبر من j). 16.31: اللفة الأولى تحسب d. والتانية recursive: لو المجموعة الحالية (بادئة طولها k) تكفيها صفحة، اعمل صفحة عمقها k وخلّي الـ 2^(d−k) خانة بتوعها يشاوروا عليها، وإلا اقسم المجموعة على البت k. 16.32: 8 pointers = 2^(d−k) = 8، ومع d = 4 يبقى k = 1. يعني محتاجين صفحة فيها مفاتيح قليلة، وكل مفاتيحها بتبدأ بـ 0، وفي نفس الوقت حتة تانية في الجدول تجبر الدليل يوصل لـ 4 بت.
:::

:::solution
```

        d = 4, directory size 16, 5 pages
       page k=4  (1 dir entry): 010000001(201) 010010001(221) 010011011(233)
       page k=4  (1 dir entry): 010100000(240) 010111011(273) 010111100(274)
       page k=1  (8 dir entries): 100000001(401) 101110010(562) 111111001(771)

      M = 3, W = 6. Keys 0,1,2 (leading bit 0: page never splits).
      Keys 32,33,36,37 = 100000,100001,100100,100101 (LCP 100: force d = 4):
        d = 4, directory size 16, 5 pages
       page k=1  (8 dir entries): 000000(000) 000001(001) 000010(002)
       page k=4  (1 dir entry): 100000(040) 100001(041)
       page k=4  (1 dir entry): 100100(044) 100101(045)

```

16\.31: البناء من المصفوفة المترتبة طلّع نفس الجدول اللي طلع من الـ inserts بالظبط (d = 4، 3 صفحات فيها items)، بس من غير الصفحتين الفاضيين اللي الـ split سابهم. ده لأن اللفة التانية مابتعملش صفحة لبادئة مفيهاش مفاتيح، وبتخلّي الخانة تشاور على صفحة أعلى. والمكسب هنا إن كل item بيتكتب مرة واحدة، من غير ولا split.

:::
