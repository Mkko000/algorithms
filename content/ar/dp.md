أقسام الكتاب: 5.3 Dynamic Programming (Programs 5.10–5.13, Property 5.3)

Divide-and-conquer بيشتغل حلو لما الجزئين **مستقلين**. بس لو الجزئين بيتداخلوا — نفس المسألة الصغيرة بتظهر في الفرعين — الريكيرشن بيعيد نفس الشغل آلاف ومليارات المرات. الحل بسيط لدرجة إنه يضحّك: **اكتب الإجابة في ورقة وماتحسبهاش تاني.** ده الـ dynamic programming.

:::goal هدف الدرس:
تفهم ليه Fibonacci الريكيرسف أسّي، تحوّل أي دالة ريكيرسف لنسخة DP بطريقتين (bottom-up وtop-down)، تحل مسألة الشنطة (knapsack)، وتعرف إمتى الـ DP مش هينفع.
:::

## المشكلة: Fibonacci (Program 5.10)

```c listing="Program 5.10"
int F(int i)
  { if (i < 1) return 0;
    if (i == 1) return 1;
    return F(i-1) + F(i-2); }
```

شكلها بريء ومطابق للتعريف. بس `F(i-1)` نفسها بتنادي `F(i-2)` تاني، وكل واحدة بتتفرّع… عدد النداءات بيكبر زي F(N) نفسها، يعني تقريبًا φ^N حيث φ ≈ 1.618. سادجوك بيقولها بشكل عملي: لو F(N) خدت ثانية، F(N+9) هتاخد أكتر من دقيقة، وF(N+18) أكتر من ساعة.

```
calls to compute F(N): naive vs top-down memo
  N=10  naive=     177  memo= 19
  N=20  naive=   21891  memo= 39
  N=30  naive= 2692537  memo= 59
```

شوف العمود الأول بيتضرب في ~11 كل 5 خطوات (φ⁵ ≈ 11). والتاني بيزيد 10 بس.

## الحل الأول: Bottom-up

احسب القيم بالترتيب من الأصغر للأكبر، وكل قيمة جديدة من اللي قبلها:

```c
F[0] = 0; F[1] = 1;
for (i = 2; i <= N; i++) F[i] = F[i-1] + F[i-2];
```

خطي. والمطلوب الوحيد: تعرف **ترتيب** يضمن إن كل قيمة محتاجها اتحسبت قبلها. في Fibonacci الترتيب واضح؛ في مسائل تانية بيبقى أصعب.

## الحل التاني: Top-down / memoization (Program 5.11)

سيب الدالة الريكيرسف زي ما هي، وزوّد سطرين بشكل **ميكانيكي**: أول حاجة، شوف لو القيمة محفوظة رجّعها. آخر حاجة، احفظ القيمة قبل ما ترجّعها.

```c listing="Program 5.11"
int F(int i)
  { int t;
    if (knownF[i] != unknown) return knownF[i];
    if (i == 0) t = 0;
    if (i == 1) t = 1;
    if (i > 1)  t = F(i-1) + F(i-2);
    return knownF[i] = t; }
```

الميزة: مش محتاج تفكّر في الترتيب — الريكيرشن بيكتشفه لوحده. وكمان بيحسب بس القيم اللي فعلًا محتاجها.

:::tip Property 5.3
الـ DP بيقلّل زمن الدالة الريكيرسف لحد أقصاه «زمن حساب الدالة لكل المعاملات الأصغر من أو تساوي المعامل المطلوب»، لو اعتبرنا كل نداء ريكيرسف تكلفته ثابتة. يعني: عدد القيم المختلفة × الشغل لكل قيمة.
:::

## مسألة الشنطة (Knapsack)

حرامي داخل مخزن بشنطة سعتها M. فيه N **نوع** من الحاجات، كل نوع ليه حجم وقيمة، ومن كل نوع كميات مش محدودة (ده تعريف الكتاب). عايز أقصى قيمة. مثال الكتاب:

<table>
<tr><th>النوع</th><th>A</th><th>B</th><th>C</th><th>D</th><th>E</th></tr>
<tr><td>الحجم</td><td>3</td><td>4</td><td>7</td><td>8</td><td>9</td></tr>
<tr><td>القيمة</td><td>4</td><td>5</td><td>10</td><td>11</td><td>13</td></tr>
</table>

الريكيرشن (Program 5.12): «لكل نوع يدخل، جرّب تحطه، وحل الباقي لسعة أقل». `knap(cap) = max(knap(cap − size[i]) + value[i])`. ونفس مرض Fibonacci: `knap(10)` هتتحسب من مسارات كتير جدًا.

Program 5.13 هو نفس التحويل الميكانيكي: `maxKnown[cap]` للقيمة، و`itemKnown[cap]` عشان نعرف **أنهي حاجة** اخترناها ونرجع نبني الحل.

```
knapsack top-down  (cap=17): 24
items used: A(size 3, value 4) C(size 7, value 10) C(size 7, value 10)

calls: recursive vs top-down memo
  cap=10  recursive=       16  memo=  14
  cap=20  recursive=      315  memo=  60
  cap=30  recursive=     6235  memo= 110
  cap=40  recursive=   122118  memo= 160
```

الريكيرسف بيتضاعف حوالي 20 مرة كل 10 وحدات سعة. الـ memo خطي: كل سعة من 0 لـ M بتتحسب مرة وبتجرّب N نوع.

ومن Property 5.3 مباشرة (الكتاب بيستنتجها بعدها): الـ DP بيحل الـ knapsack في زمن متناسب مع **N·M**.

## إمتى الـ DP ينفع وإمتى لأ؟

* **ينفع** لما المسائل الصغيرة **بتتكرر** (overlapping)، وعدد القيم المختلفة معقول تخزّنه.
* **مالوش لازمة** في divide-and-conquer اللي أجزاؤه مستقلة (زي mergesort أو max): مفيش حاجة بتتكرر أصلًا، فالحفظ مجرد مساحة ضايعة.
* **مش هينفع** لو المعامل مش عدد صحيح صغير (حقيقي، أو نص طويل) — محتاج symbol table بدل مصفوفة، وده بيكلّف.

:::problem
«Dynamic programming» اسم مالوش علاقة بالبرمجة الديناميكية. Richard Bellman اختاره في الخمسينات، و«programming» وقتها كانت معناها «تخطيط/جدولة» زي «linear programming». الفكرة الحقيقية: جدول بتملاه.
:::
