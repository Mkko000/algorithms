أقسام الكتاب: 16.4 Extendible Hashing (Programs 16.5–16.8، Definition 16.3، Properties 16.4–16.5) · 16.5 Perspective

الـ B tree بيدّي logM N probe — 3 أو 4. طب ينفع نعمل أحسن؟ الـ hashing في الذاكرة بيدّي probe واحد تقريبًا. المشكلة إن الـ hash table لما بيكبر لازم يتعاد بناؤه كله (rehash)، وده على الديسك مستحيل لملف ضخم. الـ extendible hashing (Fagin وNievergelt وPippenger وStrong، 1979) بيجمع الاتنين: 2 probe لأي بحث، ومفيش rehash كامل أبدًا.

هدف الدرس: تفهم الـ directory والـ pages والعلاقة بالـ tries، تتبّع الـ split ومضاعفة الـ directory خطوة بخطوة، تحسب حجم الـ directory والصفحات، وتطلع بخريطة كاملة لكل طرق البحث في الكتاب.

16.4 Extendible Hashing

الفكرة

خد أول d بت من الـ hash بتاع المفتاح، واستخدمهم index في directory فيه 2d خانة. كل خانة بتشاور على page فيها لحد M item. البحث: probe للـ directory (أو هو في الذاكرة أصلًا) + probe للـ page. خلاص.

Definition 16.3: الـ extendible hash table من رتبة d هو directory فيه 2d reference لـ pages فيها لحد M item بمفاتيح. الـ items في كل page متطابقين في أول k بت، والـ directory فيه 2d−k pointer للـ page دي، بيبدأوا من الخانة اللي أول k بت فيها هم البتات دول.

يعني page ممكن «يشاور عليها» أكتر من خانة. الـ k ده اسمه local depth للـ page، وd هو الـ global depth. لو k < d، الـ page بتغطّي 2d−k خانة متتالية.

الـ insert: split أو مضاعفة (Programs 16.6–16.8)

  1. احسب أول d بت، روح للـ page، حط الـ item لو فيه مكان.
  2. لو الـ page مليانة وk < d: قسمها على البت رقم k+1. اعمل page جديدة، وزّع الـ items على حسب البت ده، وخلّي نص الخانات اللي كانت بتشاور على القديمة تشاور على الجديدة. باقي الـ directory ماتغيّرش!
  3. لو الـ page مليانة وk = d: لازم الأول نضاعف الـ directory (d يزيد واحد، كل خانة تتنسخ مرتين)، وبعدين نقسم.

اتفرّج على الـ stepper: نفس المفاتيح الأوكتال بتاعة الكتاب بـ M = 4. لاحظ إن معظم الـ inserts بتدخل على طول، وإن الـ split بيلمس page واحدة بس، وإن مضاعفة الـ directory بتحصل نادرًا وبتنسخ pointers بس (مش بيانات).

Property 16.4: الـ extendible hash table المبني من مجموعة مفاتيح بيعتمد على قيم المفاتيح بس، مش على ترتيب إدخالها.

ليه؟ لأنه في الحقيقة trie (الدرس 35)! كل page = شجرة فرعية في الـ trie المبني على البتات، متقطوعة عند المستوى اللي فيه ≤ M مفتاح. والـ directory هو الـ trie ده «متسطّح» لمصفوفة بعمق d. والـ trie مستقل عن الترتيب (Property 15.2)، فالـ hash table كمان.

Property 16.5: بصفحات بتشيل M item، الـ extendible hashing بيحتاج حوالي 1.44 (N/M) صفحة لملف فيه N item في المتوسط. والعدد المتوقع للخانات في الـ directory حوالي 3.92 (N1/M)(N/M).
N=200000, M=32: directory depth d=14 (16384 entries), 8845 pages, 70.7% average fill

8845 صفحة مقابل 9000 متوقعة، ونفس الـ 69–71% امتلاء زي الـ B tree (مش صدفة: الاتنين بيعملوا split نصّين). وكل بحث = قراية page واحدة (والـ directory في الذاكرة). والـ directory؟ الصيغة بتدّي 3.92 × 2000001/32 × 6250. لاحظ إن N1/M هنا ≈ 1.46 (لأن M = 32 صغيرة نسبيًا)، والكتاب بيقول إن في المدى العملي N1/M قريبة من 1 فالـ directory عمليًا حوالي 4(N/M) خانة. وكمان الحجم لازم يبقى قوة لـ 2، فالقيمة الحقيقية بتتذبذب حوالين المتوسط ده (الكتاب بيقول كده صراحة). إحنا طلع معانا 214 = 16384 — يعني الـ directory أكبر من عدد الصفحات بحوالي الضعف، وكل pointer بس 8 بايت، فده رخيص.

نقطة الضعفلو المفاتيح (أو الـ hash بتاعها) مش عشوائية — مثلًا M+1 مفتاح بيشتركوا في أول 20 بت — الـ directory هيتضاعف 20 مرة عشان يفصلهم! حجم الـ directory ممكن ينفجر. عشان كده لازم hash function كويسة، وفيه نسخ بتحط حد أقصى لـ d وتستخدم overflow pages لو حصل كده.

16.5 Perspective

أهم تطبيق لطرق الفصل ده: indexes لداتابيز ضخمة على الديسك. بس سادجوك بيحذّر: تحويل الكود ده لـ file system حقيقي شغل كبير — لازم تقرا وتكتب من الديسك فعلًا، تظبط البارامترات (حجم الـ page والـ directory) على الهاردوير بالظبط، وتهتم بالـ reliability (لو الكهربا قطعت في نص split؟). كل ده برّه نطاق الكتاب.

بس لو عندك virtual memory، الكود زي ما هو بيشتغل: الـ page miss في الـ cache تقريبًا = probe. ومع الـ B tree، الجذر دايمًا في الـ cache، فالبحث العادي بيعمل 1–2 miss. ومع الـ extendible hashing، الـ directory غالبًا مش كله في الـ cache، فأسوأ حالة 2 miss (directory + page).
