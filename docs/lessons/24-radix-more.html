MSD radix sort سريع على الملفات الكبيرة بس بيتخنق في الصغيرة (الصناديق الفاضية). quicksort كويس بس بيعيد قراية نفس البادئات في كل مقارنة. الدرس ده فيه خوارزميتين بتحلّوا المشكلتين بطرق مختلفة تمامًا: واحدة بتمزج quicksort مع الـ radix، والتانية بتمشي من آخر المفتاح — وده شكله غلط لحد ما تفهم ليه هو صح.

هدف الدرس: تكتب 3-way radix quicksort وتعرف ليه هو الاختيار الأول لترتيب نصوص، تكتب LSD radix sort وتفهم ليه الثبات شرط أساسي، تقارن كل الـ radix sorts بخواصها الرياضية، وتشوف إزاي ترتّب من غير ما تقرا كل البتات.

10.4 Three-Way Radix Quicksort (Program 10.3)

خد 3-way quicksort بتاع الدرس 18، وغيّر حاجة واحدة: بدل ما تقارن المفتاح كله، قارن الحرف رقم D بس. قسّم لتلات: حرفهم أصغر، حرفهم مساوي، حرفهم أكبر. الأصغر والأكبر رتّبهم بنفس D. والمساوي؟ كلهم بيتفقوا في الحرف D، فرتّبهم بالحرف D+1.

#define ch(A) digit(A, D)
void quicksortX(Item a[], int l, int r, int D)
  { int i, j, k, p, q; int v;
    if (r-l <= M) { insertion(a, l, r); return; }
    v = ch(a[r]); i = l-1; j = r; p = l-1; q = r;
    while (i < j)
      { while (ch(a[++i]) < v) ;
        while (v < ch(a[--j])) if (j == l) break;
        if (i > j) break;
        exch(a[i], a[j]);
        if (ch(a[i])==v) { p++; exch(a[p], a[i]); }
        if (v==ch(a[j])) { q--; exch(a[j], a[q]); } }
    if (p == q)
      { if (v != '\0') quicksortX(a, l, r, D+1);
        return; }
    if (ch(a[i]) < v) i++;
    for (k = l; k <= p; k++, j--) exch(a[k], a[j]);
    for (k = r; k >= q; k--, i++) exch(a[k], a[i]);
    quicksortX(a, l, j, D);
    if ((i == r) && (ch(a[i]) == v)) i++;
    if (v != '\0') quicksortX(a, j+1, i-1, D+1);
    quicksortX(a, i, r, D); }

تفاصيل مهمة: لو الحرف المساوي هو '\0'، المفاتيح في النص متطابقة وخلصت — مفيش D+1. وp == q معناها كل المفاتيح نفس الحرف، فانقل للحرف اللي بعده على طول من غير تقسيم.

ليه ده أحسن من MSD؟ مفيش R عدّاد في كل نداء — بالظبط 3 أجزاء. ومفيش مساحة إضافية (في المكان). وليه أحسن من quicksort؟ البادئة المشتركة بتتقري مرات قليلة بدل مرة في كل مقارنة:

N=100000, 2N ln N = 2302585
  random words             3-way radix:   2360255 byte compares | quicksort+strcmp:   4733381 char compares
  URLs (shared prefix)     3-way radix:   7722062 byte compares | quicksort+strcmp:  61933224 char compares
  5 distinct keys          3-way radix:   2007782 byte compares | quicksort+strcmp:  14041372 char compares

على الكلمات العشوائية: قريب جدًا من 2N ln N — Property 10.5: 3-way radix quicksort بيستخدم حوالي 2N ln N مقارنة بايت في المتوسط، لمفاتيح بأي طول. نفس رقم quicksort العادي، بس المقارنات بايت واحد مش مفاتيح كاملة. وعلى الـ URLs: 8 مرات أقل.

القاعدة العمليةترتيب نصوص عامة (أسماء، URLs، مسارات ملفات)؟ 3-way radix quicksort. سريع، في المكان، ومتأقلم مع المفاتيح المكررة والبادئات الطويلة. ونفس الشجرة الضمنية بتاعته هي الـ TST (الدرس 37).

10.5 LSD Radix Sort (Program 10.4)

الفكرة اللي شكلها مجنونة: رتّب على آخر حرف، وبعدين على اللي قبله، وهكذا لحد أول حرف. بعد ما تخلص، الملف مترتب.

void radixLSD(Item a[], int l, int r)
  { int i, j, w, count[R+1];
    for (w = bytesword-1; w >= 0; w--)
      { for (j = 0; j < R; j++) count[j] = 0;
        for (i = l; i <= r; i++)
          count[digit(a[i], w) + 1]++;
        for (j = 1; j < R; j++)
          count[j] += count[j-1];
        for (i = l; i <= r; i++)
          aux[count[digit(a[i], w)]++] = a[i];
        for (i = l; i <= r; i++) a[i] = aux[i-l]; } }

ليه صح؟ بالاستقراء: بعد ما رتّبنا على آخر k حرف، الملف مترتب على آخر k حرف. لما نرتّب على الحرف رقم k+1 من الآخر: اللي حرفهم مختلف بيتحطوا صح. واللي حرفهم متساوي؟ لازم يفضلوا بالترتيب اللي اللفات اللي فاتت عملته. ده بالظبط معنى الثبات. key-indexed counting مستقر (الدرس 16)، فالخوارزمية شغالة. لو استخدمت ترتيب مش مستقر في أي لفة، كل حاجة بتبوظ.

ace add bad bed bee cab dab dad ebb fad fed fee

ولو R = 2، اسمها straight radix sort: بت بت من اليمين.

أقدم من الكمبيوترماكينات فرز الكروت المثقّبة القديمة كانت بتعمل LSD بالظبط: العامل يحط الرزمة كلها، الماكينة توزّعها على 10 صناديق حسب آخر عمود، العامل يلمّها بالترتيب ويحطها تاني على العمود اللي قبله. الثبات كان بييجي «ببلاش» من إن الماكينة بتحافظ على ترتيب الكروت في كل صندوق.

R = 2⁸ أسرع حاجة: لفّات أقل من 2⁴، وعدّاداته (256) بتقعد في الكاش بعكس 2¹⁶ (65536). و10 مرات أسرع من qsort بتاع المكتبة. بس الكتاب بينبّه: LSD محتاج بافر بحجم N، ومش متأقلم مع المدخل (بيعمل نفس الشغل على أي ملف)، وصعب على مفاتيح متغيّرة الطول.

الـ «sublinear» بتاع MSD

من Property 10.2 و10.4: MSD بيفحص بس البتات اللي محتاجها عشان يميّز المفاتيح عن بعض — تقريبًا lg N بت من كل مفتاح عشوائي. الكتاب: ترتيب مليون مفتاح 64 بت عشوائي بيبص على أول 20–30 بت بس، يعني أقل من نص البيانات. شفنا ده في الدرس 23 (15–21% من البايتات).

10.7 ترتيب «تحت الخطي»

خد الفكرة لآخرها: لو المفاتيح عشوائية، لفّة key-indexed counting واحدة على أول lg N + شوية بتات، هتسيب الملف شبه مترتب: المفاتيح اللي في نفس الصندوق قليلة جدًا. وinsertion sort على ملف شبه مترتب خطي (Property 6.4).

1 pass on top 20 bits + insertion: 0.017s, insertion moves = 261116 (0.25 per key)

ربع نقلة لكل مفتاح في الـ insertion sort! والكتاب بيقول إن الطريقة دي (لفّة على البتات الأولى + insertion) ممكن تبقى أسرع حاجة لمفاتيح عشوائية — بس بشرط: لازم مساحة للعدّادات (2^20 = مليون هنا)، ولازم المفاتيح فعلًا موزّعة بانتظام. لو المفاتيح متكتّلة (كلها بتبدأ بنفس البتات)، الـ insertion sort يرجع N².

«أسرع من N log N» مش ببلاشكل الـ radix sorts بتفترض إن المفتاح يتقسّم لأرقام وإن الـ digit رخيص. لو المقارنة معقدة (ترتيب قاموسي عربي بقواعد، أو تواريخ بصيغ مختلفة)، اللي معاك هو less بس — وساعتها N log N هو الحد.

في 3-way radix quicksort، الجزء «المساوي» بيترتب على إيه؟

كلهم بيتفقوا في D، فالفرق بينهم لازم يكون بعده. (إلا لو D كان '\0'، يبقوا متطابقين.)

LSD radix sort استخدم quicksort في كل لفّة بدل key-indexed counting. هيحصل إيه؟

كل LSD قايم على إن المتساويين في الحرف الحالي يحتفظوا بترتيبهم من الحروف اللي بعده.

LSD على أعداد 64 بت بـ R = 2¹⁶. كام لفّة؟

Property 10.6: w / lg R = 64 / 16.
